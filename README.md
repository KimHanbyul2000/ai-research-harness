# ai-research-harness

재현 가능한 연구데이터 분석을 위한 **AI 작업 골격**.
3단 git 추적 · 승격 관문 · 분석 기록 서식으로 이루어져 있다.

---

## 무엇을 푸는가

> **코드는 틀리면 멈추지만, 분석은 틀려도 숫자가 나온다.**

AI 도구를 쓰면 분석이 빨라진다. 그런데 분석의 실패 양상은 정지가 아니라 **조용히 틀린 채로
계속 가는 것**이다. 빨라질수록 이 위험이 커진다. 구체적으로는 이런 일이 생긴다.

| 문제 | 실제로 무슨 일이 생기나 |
|---|---|
| 판정 기준이 바뀌면 과거 분석이 조용히 무효가 된다 | 기준을 고친 뒤 일부 대상에만 재적용하고 넘어감. **재적용을 다 안 했다는 사실 자체를 모른다** |
| 음성 결과가 사라진다 | "조건 만족 8개"만 남고, 탈락한 대상이 **어디서 왜** 떨어졌는지는 안 남음. 기준이 또 바뀌면 처음부터 |
| 결론이 몇 개 데이터포인트에 걸려 있는데 그게 안 남는다 | 한두 개 차이로 갈린 판정이 강한 결론처럼 보고됨 |
| AI가 만든 코드가 검토 없이 본체에 쌓인다 | AI는 빠르게 많은 파일을 바꾼다. 전부 읽을 수 없다 |

이 저장소는 그 넷에 대한 **구조적 대응**이다. 도구를 더 쓰는 방향이 아니라, **판단은 사람이
유지하되 그 판단이 기록·재현·검증되도록 강제하는** 방향이다.

## 두 개의 기둥

### 1. 분석 실패를 데이터로 보존한다

분석 하나 = 폴더 하나이고, 안에 세 파일이 **항상** 같이 있다.

```
out/YYYYMMDD_<주제>/
├── 00_설계목표.md   ← 실행 '전'에 쓴다 (목적 · 방법 · "정한 것 | 값 | 이유")
├── run.py           ← 실행 코드
└── 01_결과해석.md   ← 실행 '후'에 쓴다
```

`00`이 `run.py`보다 **먼저** 존재한다는 것이 핵심이다. 그리고 `01`에는 통과분만이 아니라
**탈락 사유를 단계별로 분해해** 남기고, 기준이 바뀌었으면 **어디까지 재적용했는지 커버리지
표**를 남기며, 재분석은 **옛 기준으로 이전 결론이 재현되는지 `assert`**로 막는다.

→ 규칙: [`docs/분석폴더_규칙.md`](docs/분석폴더_규칙.md) · 서식: [`templates/`](templates/) ·
채워진 예시: [`examples/`](examples/)

### 2. git 추적을 3단으로 나눠 관문을 세운다

| 층 | 위치 | git | 성격 |
|---|---|---|---|
| 1. 작업공간 | `out/` → `archive/` | **추적 안 함** | 자유롭게 만들고 버린다 |
| 2. 스냅샷 | `bootstrap/` | 추적함 | 드라이버 **사본만** |
| 3. 라이브러리 | `lib/`, `tests/` | 추적함 | **승격 통과분만** |

승격 관문은 **둘 다** 만족해야 한다 — ① 의존성 없음 ② **두 번째 사용자 있음**.

②가 왜 필요한지는 실제 사고에서 나왔다. ①만으로 판단하다 탐색용 도구가 승격됐다가 8일
만에 되돌려졌고, 후속작은 하루 만에 돌아왔다. 되돌릴 때 드러난 값이 이랬다.

> **탐색 도구 하나가 저장소 회귀 테스트의 70%(136개 중 95개)를 차지하고 있었다.**

→ 규칙: [`docs/승격기준.md`](docs/승격기준.md) · 실물: [`.gitignore`](.gitignore)

## 도입하기

```bash
git clone https://github.com/KimHanbyul2000/ai-research-harness
```

**최소 단위 — 두 가지만 먼저 시작한다.**

1. 분석 폴더마다 **`00_설계목표.md`를 실행 전에** 쓴다 (목적 · 방법 · 정한 것과 이유).
2. 탐색 코드는 추적하지 않고, **두 번째 사용자가 생길 때만** 공용 라이브러리로 올린다.

나머지(커버리지 감사 · 재현 `assert` · 회귀 테스트)는 이 둘이 돌아간 뒤에 붙인다.
한 번에 전부 도입하면 규칙이 지켜지지 않고, 지켜지지 않는 규칙은 없는 것보다 나쁘다.

**전제 조건 3가지**

- 프로젝트 규칙이 **지속되는 파일**로 남는 AI 도구 (세션마다 자동으로 읽히는 것)
- 원본 데이터 보관 — 재현 검산이 성립하려면 다시 돌릴 수 있어야 한다
- **규칙을 쓸 담당자 한 명** — 오류 발견 → 규칙 작성 → 자동 적용의 고리가 닫혀야 한다

마지막이 가장 중요하다. 이 골격이 작동하는 이유는 도구가 좋아서가 아니라 **오류 하나당
규칙 한 줄을 쓰는 비용이 싸서**다. 그 한 줄을 쓸 사람이 없으면 고리가 닫히지 않는다.

## 구성

```
├── CLAUDE.md                    AI 에이전트가 세션마다 읽는 규칙서 (골격)
├── .gitignore                   3단 추적의 실물
├── docs/
│   ├── 승격기준.md               관문 ①②, 강등, 70% 사례
│   └── 분석폴더_규칙.md           3종 세트와 남겨야 할 네 가지
├── templates/                   빈 서식 (00 · 01 · run.py)
├── examples/                    채워진 예시 1건 — 탈락 사유 표 포함
└── lib/                         승격 통과분이 오는 곳 (비어 있음)
```

## 이 저장소에 없는 것

- **도메인 코드.** 분석 로직은 각자 분야의 것이다. `lib/`는 비어 있다.
- **실행 가능한 파이프라인.** 이건 프레임워크가 아니라 **작업 방식의 골격**이다.
  `examples/`의 코드도 모양을 보여주기 위한 것으로, 그대로 돌아가지 않는다.
- **실제 연구 데이터.** 예시의 값은 전부 가상이다.

## 배경

개인 연구 워크플로(스파이킹 신경망 시뮬레이션의 데이터 분석, 2026년 5월~)에서 도메인에
의존하지 않는 부분만 추출한 것이다. 규칙은 대부분 **실제로 사고가 난 뒤에** 추가됐고,
그 계기를 각 문서에 날짜와 함께 남겼다. 이유를 모르는 규칙은 나중에 지워지기 때문이다.
